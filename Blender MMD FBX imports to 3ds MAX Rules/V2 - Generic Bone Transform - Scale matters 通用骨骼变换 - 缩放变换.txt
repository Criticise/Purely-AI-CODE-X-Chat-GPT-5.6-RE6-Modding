通用化骨骼缩放，让MAX即使将骨骼转换成Dummy也能正常显示场景！

序言：骨骼变换问题的由来

本次遇到的问题来自这样的转换流程：BLENDER 的 MMD TOOLS 插件将 MMD 转换成 BLENDER 模型之后，BLENDER 能够承接这种带缩放的骨骼，保证模型和场景正常显示。但是，同一套骨架经 FBX 导入 3DS MAX、被转换成 DUMMY 以后，骨骼继承的大倍率缩放也会放大 DUMMY 的辅助方框。大量方框和骨骼连接线重叠，就会出现满屏白色线框的现象。

这就是本次 BUG 的根源原因：这类骨架缩放在 BLENDER 中能够正常显示，而 MAX 转换成 DUMMY 时，会把继承的缩放带入辅助对象的显示尺寸，造成方框膨胀。

因此，骨骼通用变换需要在保持人物大小、关节世界位置和蒙皮效果的前提下，换算骨架缩放并同步修正绑定数据，让 MAX 即使将骨骼转换成 DUMMY，也能正常显示场景。下面记录的是这次已经通过 Max 实测和用户导入确认的处理经验。

记录日期：2026-09-08
验证环境：3ds Max 2026；FBX 导入时启用 ImportBoneAsDummy。
验证状态：独立 Max 批处理检查通过，用户实际导入后确认“效果非常好”。

一、这次成功的方法

把骨架继承的大倍率换算到骨骼的局部位置数据中，使骨节点的世界缩放接近正常参考值；同时更新蒙皮绑定矩阵，保持人物大小、关节世界位置、骨架长度和蒙皮效果。

变小的是 Dummy 的辅助方框，以及骨节点变换基底的尺度。人物和骨架所占的世界空间保持原样。

本次保留了全部 172 根骨头，包括末端骨；保留骨名、ID、父子层级、网格、材质和全部蒙皮权重。没有通过删除骨头来改善画面。

“通用化”是可复用的处理原则。本次实现和验证针对下面的静态、统一正缩放样本；处理其他结构时，需要先检查其变换和绑定约定。

三、本次缩放换算步骤

本样本满足以下条件：
  - 单一 Armature 根容器，其父级为场景根。
  - Armature 使用统一、正数缩放。
  - 全部 172 根骨头位于该容器下，骨架子树里没有网格。
  - InheritType=1；无 PreRotation、PostRotation、Pivot、Offset。
  - 无动画对象；网格位于骨架子树之外。

定义：
  s = Armature 原来的统一缩放。
  q = 希望骨头达到的参考世界缩放。
  k = s / q，即本次需要移除的统一倍率。

本次取《接缝》骨骼世界缩放的中位数作为 q：
  s = 39.37007874015747
  q = 1.000055262654
  k = 39.36790316534614

具体修改：

1. Armature 的 Lcl Scaling 除以 k。
2. 全部后代骨头的 Lcl Translation 乘以 k。
3. 保留骨头和容器的旋转；保留骨头局部缩放的原始浮点细节。
4. Armature 本身的位置保持原值。
5. 给全部骨头复制参考文件的 LODBox=1。
6. 保留 LimbNode / Skeleton 类型，以及原有 Size=1.5。
7. 按下一节同步更新全部相关绑定矩阵。

这样，大倍率会从骨节点的世界基底中消除，同时由平移数据的换算补偿骨架的空间位置。

其他文件的 k 应从其实际数据计算，不能把 39.37 写成所有 FBX 共用的固定倍率。目标 q 可以取经验证的正常参考骨节点尺度，或者在明确单位约定后采用约 1 倍的目标。

四、蒙皮绑定必须同步更新

下面的公式对应本次二进制解析器直接读取、改写的 FBX 序列化矩阵，采用行向量约定：
  点变换：p_world = p_local * W
  平移位于 16 元素数组的索引 12、13、14。

此样本的原始 Cluster 数组满足：
  Transform * TransformLink = MeshBind

其中，Transform 在本次序列化数据中表示网格到骨骼绑定空间的变换，TransformLink 表示骨骼绑定世界矩阵。

使用 FBX SDK 或其他库时，应先确认其接口返回值的语义；不能直接把这里的原始数组公式当成所有 SDK 的 GetTransformMatrix / SetTransformMatrix 公式。

令：
  D = diag(k, k, k, 1)
  Dinv = diag(1/k, 1/k, 1/k, 1)

对于 Armature 和全部受影响骨头：
  World_new = Dinv * World_old

这会把世界矩阵的 3 x 3 基底除以 k，保留世界平移。

对于每个相关 Cluster：
  TransformLink_new = Dinv * TransformLink_old
  Transform_new = Transform_old * D

对应的数组操作：
  - TransformLink：索引 0、1、2、4、5、6、8、9、10 除以 k。
    索引 12、13、14 的平移不变。
  - Transform：前三个空间列乘以 k，包含索引 12、13、14 的平移分量。
    齐次列保持原样。

必须成立的两个等式：
  Transform_new * TransformLink_new
    = Transform_old * TransformLink_old

  Transform_new * World_new
    = Transform_old * World_old

第一个等式保持网格绑定空间；第二个等式保持当前姿态下的蒙皮变换。

本次还处理了两个容易遗漏的地方：

1. TransformAssociateModel
   全部 276 个 Cluster 都带有此矩阵。先验证它对应原 Armature 的世界矩阵，再对它做 Dinv 左乘，保持它与更新后的 Armature 一致。
   其他文件若关联不同对象，应根据真实关联对象的变换计算，不能一律套 Armature 的倍率。

2. BindPose / PoseNode / Matrix
   骨头和 Armature 的全局绑定姿态矩阵做 Dinv 左乘。
   网格的绑定姿态矩阵保持原样。
   本次两个 BindPose 共更新 278 个相关 PoseNode；其余条目保持原样。
   本样本的 PoseNode 均为全局矩阵。含局部 PoseNode 的文件需要按局部空间另外计算。

全部 276 个 Cluster 均同步处理，包含没有非零权重的 Cluster，以保持原有绑定记录完整。

ENGLISH VERSION

Normalizing Bone Scale So MAX Can Display the Scene Correctly Even After Converting Bones to Dummy Objects!

Preface: Where the Bone Transform Problem Comes From

The problem encountered here arose from this conversion workflow: after BLENDER's MMD TOOLS plugin converts an MMD model into a BLENDER model, BLENDER can handle the scaled bones and display the model and scene correctly. However, when the same skeleton is imported into 3DS MAX through FBX and converted to DUMMY objects, the large scale inherited by the bones also enlarges the DUMMY helper boxes. Numerous boxes and bone connection lines overlap, filling the screen with white wireframes.

This is the root cause of the BUG observed in this case: BLENDER can display this kind of skeleton scale correctly, whereas MAX includes the inherited scale in the helper objects' display dimensions when converting the bones to DUMMY objects, causing their boxes to expand.

A reusable bone transform procedure therefore needs to adjust the skeleton scale and update the binding data together, while preserving the character's size, the joints' world positions, and the skinning result. This allows MAX to display the scene correctly even when it converts the bones to DUMMY objects. The following notes document the procedure that passed testing in Max and was confirmed by the user's actual import.

Record date: 2026-09-08
Validation environment: 3ds Max 2026; ImportBoneAsDummy enabled during FBX import.
Validation status: independent Max batch checks passed, and the user confirmed after importing the file that "the result is very good."

1. The Procedure That Worked in This Case

Transfer the large inherited skeleton scale into the bones' local position data so that the bone nodes' world scales approach the normal reference value. Update the skin binding matrices at the same time to preserve the character's size, the joints' world positions, the skeleton's lengths, and the skinning result.

What becomes smaller is the Dummy helper boxes and the scale of the bone nodes' transform bases. The world-space extent of the character and skeleton stays unchanged.

All 172 bones were retained in this case, including end bones. Bone names, IDs, parent-child hierarchy, meshes, materials, and all skin weights were preserved. No bones were deleted to improve the display.

"Generalization" refers to a reusable processing principle. This implementation and its validation cover the static sample with uniform positive scale described below. Other structures require their transform and binding conventions to be checked first.

2. Comparison Samples and Diagnosis

Reference with correct display: Generic 通用 接缝还没处理.fbx
Sample to repair: Generic 通用 无标题.fbx
Successful output: Generic 通用 无标题_接缝骨骼尺寸测试.fbx

The two original files have exactly the same bone types:
  Model type: LimbNode
  NodeAttribute type: LimbNode
  TypeFlags: Skeleton
  Bone property Size: 1.5
  InheritType: 1
  RotationOrder: 0

Key differences:

1. The reference file, Generic 通用 接缝还没处理.fbx, contains 83 bones. Most have a world scale of approximately 1.000055.
   Although its root bone b_256_1 has a scale of 366.723602, its two immediate child bones have a scale of 0.002727. Their product is approximately 1.000055, so most subsequent bones return to a scale close to 1.

2. Generic 通用 无标题.fbx contains 172 bones. Its parent, ch0100_40_00 Armature, has a uniform scale of approximately 39.37007874. The descendant bones do not cancel this factor, so the world-space basis scale of the entire skeleton is approximately 39.37.

3. The bone Dummy objects created by Max during this import have local boxes of approximately 1 x 1 x 1. After inheriting a world scale of approximately 39.37, these boxes are enlarged too. Many overlapping boxes create the visual impression of "a mass of Helper objects exploding into the scene."

3. Scale Conversion Steps Used in This Case

This sample meets the following conditions:
  - A single Armature root container whose parent is the scene root.
  - The Armature uses uniform positive scale.
  - All 172 bones are under this container, and the skeleton subtree contains no meshes.
  - InheritType=1; no PreRotation, PostRotation, Pivot, or Offset.
  - No animation objects; the meshes are outside the skeleton subtree.

Definitions:
  s = the Armature's original uniform scale.
  q = the desired reference world scale for the bones.
  k = s / q, the uniform factor to remove in this case.

The median bone world scale in Generic 通用 接缝还没处理.fbx was used as q:
  s = 39.37007874015747
  q = 1.000055262654
  k = 39.36790316534614

Specific changes:

1. Divide the Armature's Lcl Scaling by k.
2. Multiply the Lcl Translation of every descendant bone by k.
3. Preserve the rotations of the bones and container; retain the original floating-point details of the bones' local scales.
4. Keep the Armature's own position unchanged.
5. Copy LODBox=1 from the reference file to all bones.
6. Preserve the LimbNode / Skeleton types and the original Size=1.5.
7. Update all related binding matrices as described in the next section.

This removes the large factor from the bone nodes' world-space bases while compensating through translation data to preserve the skeleton's spatial positions.

For other files, k must be calculated from their actual data. Do not hard-code 39.37 as a factor shared by all FBX files. The target q can be taken from a validated reference bone-node scale, or a target of approximately 1 can be used after the unit conventions have been established.

4. Skin Binding Must Be Updated at the Same Time

The formulas below apply to the serialized FBX matrices read and rewritten directly by the binary parser used in this case. They use a row-vector convention:
  Point transformation: p_world = p_local * W
  Translation is at indices 12, 13, and 14 of the 16-element array.

The original Cluster arrays in this sample satisfy:
  Transform * TransformLink = MeshBind

In this serialized data, Transform represents the transformation from mesh space to bone binding space, and TransformLink represents the bone's bind-world matrix.

When using the FBX SDK or another library, first confirm the semantics of the values returned by its interfaces. Do not directly treat these raw-array formulas as universally applicable formulas for every SDK's GetTransformMatrix / SetTransformMatrix interfaces.

Let:
  D = diag(k, k, k, 1)
  Dinv = diag(1/k, 1/k, 1/k, 1)

For the Armature and all affected bones:
  World_new = Dinv * World_old

This divides the world matrix's 3 x 3 basis by k while preserving its world translation.

For each related Cluster:
  TransformLink_new = Dinv * TransformLink_old
  Transform_new = Transform_old * D

Equivalent array operations:
  - TransformLink: divide indices 0, 1, 2, 4, 5, 6, 8, 9, and 10 by k.
    Keep the translation at indices 12, 13, and 14 unchanged.
  - Transform: multiply the first three spatial columns by k, including the translation components at indices 12, 13, and 14.
    Keep the homogeneous column unchanged.

Two equalities must hold:
  Transform_new * TransformLink_new
    = Transform_old * TransformLink_old

  Transform_new * World_new
    = Transform_old * World_old

The first equality preserves the mesh binding space. The second preserves the skinning transformation in the current pose.

Two easily overlooked areas were also handled in this case:

1. TransformAssociateModel
   All 276 Clusters contain this matrix. First verify that it corresponds to the original Armature's world matrix, then left-multiply it by Dinv to keep it consistent with the updated Armature.
   If another file associates a different object, calculate the update from that object's actual transform. Do not apply the Armature's factor indiscriminately.

2. BindPose / PoseNode / Matrix
   Left-multiply the global bind-pose matrices of the bones and Armature by Dinv.
   Keep the meshes' bind-pose matrices unchanged.
   A total of 278 related PoseNodes were updated across the two BindPoses in this case; all other entries were kept unchanged.

7. Applicability to Other FBX Files

The current script was validated on a static skeleton with positive uniform scaling. Files with animation, constraints, multiple Armatures, meshes beneath the skeleton, nonuniform scaling, negative scaling, shear, special InheritType settings, pivots, or Pre/PostRotation require full transform evaluation and renewed validation. The simplified operation of multiplying every bone translation by k must not be applied to those cases without further analysis.

Animated files also require corresponding animation-track conversion or per-frame evaluation and rebaking, followed by validation of the complete animation. The two local-rotation experiments verified skinning consistency for those tested poses; they did not validate arbitrary animation files.

Maintain both of these criteria:
  1. Joint world positions, model dimensions, and skinning behavior must remain consistent.
  2. The scale of the Dummy display basis should be normalized to a range appropriate for the target scene.

LODBox was a reference display setting used to match the appearance in Max. The bones retained the standard LimbNode / Skeleton types. Changing type tags alone, deleting leaf bones, or changing only Size has not been validated as a replacement for this complete procedure.
